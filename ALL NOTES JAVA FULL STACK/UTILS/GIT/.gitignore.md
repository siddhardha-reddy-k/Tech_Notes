## **Topic 8: .gitignore**

**Purpose**

Tells Git which files/folders to **never track**, so they don't show up in git status, can't accidentally be git added, and never get committed.

Three main reasons you use it:

1. **Noise reduction** — generated/build files don't belong in history (e.g., compiled .class files, dist/ folders)

1. **Security** — prevents secrets from ever entering commit history (.env, API keys, credentials files)

1. **Repo size/performance** — huge folders like node\_modules/ or virtual environments shouldn't bloat the repo; every clone would download them otherwise

**Where it lives**

A file literally named .gitignore, placed in the root of your repo (you can also have nested .gitignore files in subfolders for folder-specific rules, though root-level is most common).

**Syntax Basics**

gitignore

# comment — lines starting with # are ignored

\*.log              # wildcard: ignore all files ending in .log
secret.txt          # ignore this exact file
build/              # trailing slash = ignore this folder entirely
/config.json         # leading slash = only ignore config.json in the ROOT, not subfolders
logs/\*.txt           # ignore .txt files only directly inside logs/ folder
\*\*/temp/             # ignore any folder named temp/, at any depth
!important.log       # negation — un-ignore this one file (exception to a broader rule above)

**Key syntax gotchas (asked in MCQs):**

- / at the **start** of a pattern anchors it to the root only

- / at the **end** of a pattern means "this is a folder, ignore everything inside it"

- \*\* matches across multiple directory levels

- Order matters for negation (!) — you can't un-ignore something inside an already-ignored *folder* unless the folder itself isn't fully excluded; this is a known Git quirk

**Common Patterns (real-world templates)**

For a typical Java/Node project you'll be working with:

gitignore

# Java
\*.class
target/
\*.jar

# Node
node\_modules/
npm-debug.log

# IDE
.idea/
.vscode/
\*.iml

# Environment / secrets
.env
\*.pem

# OS
.DS\_Store
Thumbs.db

GitHub actually lets you auto-generate a .gitignore template for your language/framework when creating a new repo — no need to memorize every pattern, just know the concept.

**The Untrack Gotcha (important — repeating deliberately since it's a real trap)**

.gitignore only prevents Git from tracking **new/untracked** files. If a file was already committed *before* you added it to .gitignore, Git keeps tracking it — .gitignore has zero retroactive effect.

**Fix — remove it from tracking without deleting the actual file:**

bash

```bash
git rm --cached <file>
git commit -m "Untrack file"
```

Now it stays on your disk, but Git stops watching it — and going forward, the .gitignore rule applies to it properly.

**Interview framing to remember:** *"Why is my file in .gitignore still showing up in git status?"* → answer: it was already tracked before the ignore rule was added; .gitignore doesn't retroactively untrack, you need git rm --cached.
